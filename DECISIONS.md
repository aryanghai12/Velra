# DECISIONS.md

Every place where `prompts doc/BUILD_PROMPT_v0.1.md` was ambiguous, plus each
deviation from its letter, with a one-line rationale. The spec's tie-breaker
order is applied throughout: (1) never block or visibly disturb Claude Code,
(2) preserve data, (3) choose the simplest option.

## Claude Code compatibility (§6.3, `compat`)

| # | Decision | Rationale |
|---|---|---|
| D1 | `args` exec form gated at 2.1.139, `if` field at 2.1.85, `PostCompact` at 2.1.76, PowerShell tool at 2.1.84, `SessionStart` 1.0.62, `SessionEnd` 1.0.85, `PreCompact` 1.0.48 | Versions named in the official changelog. |
| D2 | Async hooks gated at 2.1.23; `PostToolUseFailure` at 2.1.119; `PostToolBatch` at 2.1.268 | The changelog never names an introducing version for these. The floor is the earliest version with direct evidence (a changelog line, or presence verified in the shipped 2.1.268 binary). Registering an event an older Claude Code does not know risks a settings validation error, so the conservative floor is safer than guessing lower; the system degrades gracefully without all three. |
| D3 | `velra enable` falls back to reading the version from an installed VS Code extension directory (`anthropic.claude-code-<version>-…`) when `claude --version` is absent | The spec says "absent → assume latest known"; this is strictly better information, and Claude Code is frequently installed only as an IDE extension (no `claude` on PATH). Still falls back to "assume latest known". |
| D4 | The `PreCompact` `systemMessage` ("⚡ Velra checkpoint saved: …") is emitted as specified even though Claude Code documents that it discards `systemMessage` (and `continue`) on `PreCompact` and `PostCompact` | The spec mandates the output; emitting it is harmless, and it becomes visible if Claude Code ever starts surfacing it. The user-visible confirmation in practice is the delivery message on the next `SessionStart`. |
| D5 | Shell-form registrations (Claude Code < 2.1.139) write the binary path with forward slashes on Windows | Shell form runs under Git Bash there; backslashes inside a double-quoted Bash string are error-prone, forward slashes always work. |
| D5a | `VELRA_CLAUDE_VERSION` overrides version detection | Acceptance test A7 must exercise the old-version code path deterministically, and users whose Claude Code is not on `PATH` (IDE-only installs) get a way to pin the assumed version instead of falling back to "latest known". |

## Settings editing (§6.2, §6.4)

| # | Decision | Rationale |
|---|---|---|
| D6 | Edits are minimal text splices computed from `jsonc-parser` **AST byte ranges** rather than its CST mutation API | The hard requirement is that `enable` → `disable` returns a byte-identical file (A3) and that no non-Velra byte moves (A2). Splicing exact ranges — reusing the file's own comma/newline/indentation style, and restoring `[]`/`{}` when a container empties — makes that a property of the algorithm instead of a property of a third-party formatter. `jsonc-parser` is still the parser, as prescribed. |
| D7 | A backup is written only when a write will actually happen | Step 3 of §6.2 writes the backup before computing the change, but `enable` run twice must be a no-op; writing ten identical backups would evict real history from the 10-backup window. |
| D8 | Velra handlers that no longer match any desired registration (stale matchers, events unsupported by the detected Claude Code) are removed during `enable` | Otherwise a Velra upgrade or Claude Code downgrade leaves handlers that fire twice or fail; §6.2 step 5 covers only add/update. |
| D9 | When the settings file does not exist, `enable` creates it; `disable` afterwards leaves an empty `{}` file rather than deleting it | The byte-identical guarantee in §6.4 is stated for a file that existed before `enable`; deleting a file Velra created is more surprising than leaving `{}`. |
| D10 | Semantic verification (step 7) compares both documents after stripping Velra handlers **and** dropping empty `hooks`/event/group containers on both sides | Makes the comparison symmetric, so a pre-existing empty `"hooks": {}` does not read as a difference. |
| D11 | `disableAllHooks` is checked in the target settings file only, not in merged project/managed settings | Velra never reads project-level settings (§6.1); a wrong "hooks are disabled" warning is worse than a missing one. |

## Storage and reducer (§10, §11)

| # | Decision | Rationale |
|---|---|---|
| D12 | Extra secondary indexes (`ix_*`) are created alongside the normative schema | The normative schema has no index for the reducer's hot lookups (edits by session+path, commands by epoch); they change no semantics and keep the PreCompact barrier inside its 10 ms budget. |
| D13 | `trigger` is quoted as `"trigger"` in all SQL | It is a SQLite keyword; quoting avoids depending on fallback-token behaviour. |
| D14 | Turn-end scan hashing happens **outside** the batch transaction: the reducer splits the batch so a `Stop` event starts a new batch, hashes files first, then applies the event, re-checking the cursor | Hashing up to 64 files inside `BEGIN IMMEDIATE` would hold the write lock for tens of milliseconds and push concurrent hooks into the spool. |
| D15 | Spool files that fail to parse are left in place for 5 s before being quarantined into `spool/bad/` | A file may be mid-write by another process; never discard data that might still be complete. |
| D16 | Spool entries carry the project row (`root_path`, `is_git`) in addition to the event columns | The reducer needs the project root to resolve paths; the spec's "exact normalized event row" has no room for it and the extra field is ignored elsewhere. |
| D17 | Events are appended with `INSERT OR IGNORE` on `dedupe_key`, and the reducer advances its cursor to the last event it actually applied | Gives idempotent replay after a crash mid-batch (C3) without a lease. |

## Intents, files, reverts (§12, §13)

| # | Decision | Rationale |
|---|---|---|
| D18 | Revert detection collapses runs of identical hashes before searching for the return point, and uses the **latest** matching earlier version | Without collapsing, an unchanged re-observation (e.g. the `pre_edit` hash of the next edit) makes the edit that restored the original look reverted, producing a phantom dead end. |
| D19 | An observation that reapplies a dead end never also creates a new dead end | After `A→B`, revert to `A`, then `A→B` again, the re-application is the interesting fact; marking the intermediate restoring edit as a new dead end would be noise. |
| D20 | A git restore-family command counts as having touched a file only when `git_pre ≠ git_post` (or, without a pre observation, when the file no longer matches its last post-edit hash) | Prevents `git restore other.txt` from discarding edits to an unrelated file that something else had already changed. |
| D21 | `git commit` also triggers file rehashing in `pre-tool-use`/`post-tool-use`, and marks ACTIVE edits **up to and including** the edit whose hash matches the committed file as COMMITTED | §13.3 needs a "last COMMITTED marker" to exist; marking only the exact-hash edit would leave superseded earlier edits ACTIVE and render them as live attempts after they were committed. |
| D22 | `pre_edit`, `git_pre` and `original` observations that reveal an unexpected hash use mechanism `external` | §13.2 names mechanisms only for `git_post`, `post_edit` and `turn_scan`; "changed outside the agent" is the accurate description for the rest. |
| D23 | Windows path identity uses the canonical on-disk spelling where the file exists, and the project id is case-folded | §18 requires case-folded identity; canonicalizing gives a single identity per file while still displaying the real casing. |

## Commands and failures (§14)

| # | Decision | Rationale |
|---|---|---|
| D24 | Across subcommands, kind is chosen by priority `test > build > lint > git > other` rather than "first subcommand that matches anything" | `git stash && npm test` is a test run; classifying it as `git` would hide the failure that matters. |
| D25 | Failure markers are evaluated after neutralizing zero counts (`0 failed`, `0 errors`), and weak markers (`Error:`, bare `failed`, `FAIL `) are overridden by a strong pass summary on a successful exit | The literal marker list in §14 classifies `test result: ok. 3 passed; 0 failed` as FAIL. Strong markers (`FAILED`, `--- FAIL`, `error[`, `Traceback`, …) still win, so `pytest \| tail` (which masks the exit code) is still detected. |
| D26 | A `PostToolUse` shell event implies exit code 0 for outcome purposes, without storing a synthetic `exit_code` | Claude Code reports non-zero exits as `PostToolUseFailure`; `tsc` and friends print nothing on success, which would otherwise be UNKNOWN forever. |
| D27 | For `PostToolUseFailure`, the exit code and output come from parsing Claude Code's `Exit code N\n…` first line of `error` | That is the documented shape, and it is the only place a failed command's output survives. |
| D28 | Mentioned paths resolve against the command's `cwd` first, then the project root, and at most 16 are stored | Agents routinely `cd` into a subdirectory; unbounded `stat` calls would blow the reducer budget. |

## Capsule (§16)

| # | Decision | Rationale |
|---|---|---|
| D29 | With no ROOT captured, the section renders as `[ROOT_TASK_OBJECTIVE]` + `(not captured)` with no provenance parenthetical | Writing `(OBSERVED | user prompt | --:--)` would claim an observation that does not exist. |
| D30 | An UNKNOWN last-test outcome renders literally as `UNKNOWN` in STATUS | The template lists `PASS\|FAIL\|INTERRUPTED\|none`; UNKNOWN is a real stored outcome and hiding it as `none` would misreport. |
| D31 | After the §16.3 truncation ladder, additional steps (drop "Observed afterward", drop NEXT_KNOWN_TARGET, attempts → 0, failure excerpt → 0, shorter subtask/path/command caps, drop LATEST) run **only** when the result is still above the 1,000-token hard ceiling | §16.3 says to emit as-is between target and hard ceiling, but E2 requires the hard ceiling always. The extra steps make the ceiling a guarantee for any input. |
| D32 | E3 ("no causal language") is enforced on the renderer's own template text, not by rewriting evidence | Deleting the word "because" from a captured test excerpt would corrupt the evidence the capsule exists to preserve. A test asserts the template literals never contain the banned words. |
| D33 | Counted items are pluralized (`1 file`, `2 files`; `1 dead end`, `2 dead ends`) | The template's `{k} files` reads wrong at k=1; `{k} edit(s)` is kept literally as written. |
| D34 | `velra inspect` without `--checkpoint` renders with `checkpoint="preview"` and a RECOVERY line without `--checkpoint` | No checkpoint exists to reference, and §7 forbids creating one. |
| D35 | The capsule ends with `</VELRA_CONTINUATION>` and no trailing newline | Nothing depends on it and it keeps the golden snapshots unambiguous. |

## Delivery (§15)

| # | Decision | Rationale |
|---|---|---|
| D36 | The capsule is written to stdout **inside** the delivery transaction, immediately before commit; if the write fails the transaction rolls back and the continuation stays deliverable | Matches §18's accepted worst case (a crash between emit and commit re-emits once) while never losing a delivery because the commit succeeded and the write did not. |
| D37 | `reconcile` reads first and only takes the write lock when a transition is actually due | Keeps the common `UserPromptSubmit`/`PostToolUse` path to a single indexed read (§4 budgets). |
| D38 | Reconciliation also runs on `SessionStart(compact\|resume)`, `Stop` and `PostToolUseFailure` | T7 allows "any hook"; these are the events where a missed T3 would otherwise strand an ATTACHED continuation. |

## Runtime and safety (§4, §8, §9)

| # | Decision | Rationale |
|---|---|---|
| D39 | The watchdog thread takes the stdout guard before calling `exit(0)` | Guarantees the process never dies mid-write, so stdout is always either empty or one complete JSON object (§8.1 rule 2). |
| D40 | Fault injection (`VELRA_TEST_PANIC`, `VELRA_TEST_STALL_MS`) exists only under the `fault-injection` cargo feature | G2/G3 need it; shipping fault injection in release binaries does not. |
| D41 | Long output is tailed with a 1 KiB margin, redacted, then tailed again to the final size | A secret straddling the first cut would otherwise survive as an unmatched fragment. |
| D42 | The retained-payload budget is enforced by shrinking the largest text field (stdout/stderr/error/summary/prompt/command) until the serialized payload fits 16 KiB | §9.1's per-field caps (2 KiB command + 8 KiB + 8 KiB tails) can exceed the 16 KiB total; the total is the binding constraint. |
| D43 | `TZ=UTC` (and `Etc/UTC`, `GMT`, `UTC0`) forces a zero offset on every platform | Windows ignores `TZ`, and E1 requires byte-identical goldens across operating systems. |
| D44 | Unparseable stdin with a recoverable `session_id` is recorded as a `malformed` event; without one it is a silent no-op | §18 asks for both behaviours; the salvage scan is a plain substring search, no regex on the hot path. |
| D45 | The async `reduce` watchdog fires at 1,000 ms while the reducer's own deadline is 900 ms | Lets the reducer finish and commit its current batch instead of being killed mid-transaction. |

## Distribution (§5)

| # | Decision | Rationale |
|---|---|---|
| D46 | The release pipeline is a hand-written GitHub Actions workflow rather than `dist`-generated | §5.2 pins installer behaviour that `dist`'s generated installers do not offer: installing to `~/.velra/bin`, the exact final two lines, and the opt-in `--enable` flag. The workflow still produces what the spec asks for — per-target archives, SHA-256 checksums, a combined `sha256.sum`, and GitHub build-provenance attestations — and `install/homebrew/velra.rb` plus `npm/` cover the remaining channels. Keeping the installers first-party also means CI has no dependency on a release tool's version. |
| D47 | Acceptance test C1 runs 8 processes × 25 invocations by default and the full 32 × 500 when `VELRA_STRESS=1` | 16,000 process spawns take minutes on a developer laptop (and much longer on Windows). The property under test — no lost events, no duplicates — is identical at both sizes; CI runs the full shape. |
| D48 | The watchdog spools the in-flight event before `exit(0)`, and `run()` does the same after a caught panic | The 250 ms deadline previously dropped an event that was already normalized but not yet committed, which broke the §10.3 no-loss guarantee under saturation. Re-spooling a row that did commit is harmless: ingestion deduplicates on `dedupe_key`. |
| D49 | The watchdog deadline is overridable via `VELRA_TEST_WATCHDOG_MS`, only in `fault-injection` builds | C1 saturates the machine badly enough to trip the real deadline, which would measure the watchdog rather than the storage guarantee. Release binaries have no override at all. |
| D50 | `velra enable` refreshes `state.json` even when the settings file needs no change | Otherwise `doctor`'s "binary missing" finding could never be repaired by the command it tells the user to run. |
| D51 | Each log line is written with a single `write_all` | Concurrent hook processes append to the same file; two writes let their output interleave and lose line boundaries. |
| D52 | `VELRA_LOG=debug` now logs a per-phase breakdown (`stdin`, `parse`, `context`, `db-open`, `db-append`, `handler`) alongside the total | §20 asks for per-invocation timing; a single total cannot tell a slow disk from a slow reducer. Marks cost one `Instant::now()` each and are skipped entirely when debug logging is off. |
| D53 | `bench/run.sh` falls back to a built-in timer when hyperfine is absent, and reports rather than gates in that mode | Requiring hyperfine to see any numbers is a poor first run. The fallback's own spawn cost is included in every measurement, so gating on it would be measuring Python; CI installs hyperfine and gates there. `VELRA_BENCH_STRICT=1` forces gating anyway. |
| D54 | The §4 budgets are enforced on Linux only, and the Windows p99 allowance describes **marginal** cost rather than wall time | Measured on this Windows box (release, GNU target, 100k-event database): `db-open` alone is 1.3 ms and `db-append` 1.0 ms, and Python's own SQLite reproduces a 1.6 ms open on the same file — the storage engine's floor there is already above the 2 ms p50 budget. §4's Windows allowance of p99 ≤ 15 ms of *wall time* is not reachable there, and that is not a statement about Velra: the v0.1 benchmark timed a spawn control — the same binary with `VELRA_DISABLE=1`, which exits before touching the database — at a p99 of 7.2 ms against a 0.5 MiB database and 25.0 ms against a 38 MiB one. Starting a process on that machine already costs more than the whole allowance. Velra's own marginal cost over that control is +3.4 to +11.0 ms at p50 and barely moves between the two database sizes, which says the storage engine is not the constraint either; the marginal figure is the one the Windows budget should name. The p50 budgets describe Linux, which is where CI measures with hyperfine. |

## Defects found by the v0.1 benchmark (`BENCHMARK_REPORT.md`)

| # | Decision | Rationale |
|---|---|---|
| D55 | `estimate_tokens` walks the string by run instead of dividing the character count by 3.2 (§16.3) | The spec's ratio is wrong for the text the capsule actually contains. Measured with Anthropic's tokenizer, two delivered capsules cost 951 and 1,147 tokens where the spec's formula read 643 and 743 — an under-read of about a third, because bracketed tags, POSIX and Windows paths, a 26-character ULID and quoted code run at 2.07–2.16 characters per token while the prose around them runs near 4. A single ratio cannot serve both, so the estimator charges space-led words, glued words, digits and punctuation separately, plus a 1/32 margin so it errs high. The truncation ladder is unchanged and now enforces the budget it was always meant to; `tests/fixtures/tokenizer/` keeps both measured capsules as a regression guard. |
| D56 | A file observation older than one already recorded draws no conclusions, and version history is ordered by hook timestamp rather than row id | A hook that cannot reach the database spools its event; the reducer ingests it later, so it lands with its original timestamp and a *newer* row id than events that really happened after it. Read in insertion order, such a row looks like the newest state of the file. In the benchmark the `git_pre` snapshot of a `git restore` — which carries the pre-restore content by construction — arrived after the turn scan that had just opened the dead end, matched its post-edit hash, and marked it reapplied; `[DEAD_ENDS]` then vanished from the delivered capsule, because the renderer selects `reapplied = 0`. Reapplication additionally requires a *settled* source (`post_edit`, `git_post`, `turn_scan`): `git_pre`, `pre_edit` and `original` all describe the state before their event's effect and can never witness a change coming back. |
| D57 | Git effects are read from failed shell calls as well as successful ones; commit detection still requires success | `git restore x && pytest` is reported as one failed tool call whenever the suite still fails, which is the normal shape of discarding an attempt. Skipping the observation lost the revert entirely: the turn-end scan picked it up later and reported "changed outside the agent" with no command text, for a command the agent had just run itself. Every rule involved compares hashes measured after the call returned, so they hold either way. A commit is different — an edit that was never committed hashes the same as one that was — so only a call that reported success marks edits COMMITTED. |
| D58 | The `PreToolUse` Bash/PowerShell registrations drop §6.3's `if` rules (`Bash(git *)`, `PowerShell(git *)`) and filter inside the binary instead | Those rules are prefix matches. They see `git restore src/a.py` but not `cd "/path" && git restore src/a.py`, which is how an agent phrases the same command whenever it needs a working directory first, and there is no rule syntax for "git anywhere in the command line". A revert missed here has no `git_pre` snapshot at all. `hook pre-tool-use` already parses the command with the same subcommand splitter used everywhere else and returns before opening the database when no git subcommand is present, so the cost is one extra process spawn per Bash call — on a path where `PostToolUse` already matches `*`. |
| D59 | `[WORKING_FILES]` ranks by `6·named-elsewhere + 4·in_failure + 3·min(edits,3) + 2·(reads≥2) + min(reads,3)`, breaking ties towards *first* touch, rather than §16.2's `3·edits + min(reads,5) + 4·in_failure` with ties by last touch | §16.2's tie-break always favours whatever happened most recently, and a breadth-first read sweep produces dozens of files tied at a single read. In the benchmark an audit across 84 unrelated modules filled the section and evicted both files the failing test ran through. The new weights separate scarce evidence (an edit, a name in the failing output, a file another section already cites) from abundant evidence (one read), and among equally thin candidates the files the session opened with rank above the ones a late sweep touched. `inspect --section files` uses the same order, minus the bonus for files the capsule names, so the detail view matches the summary it explains. Needs `file_stats.first_touch_ms`, which is schema v2. |
| D60 | Commands quoted in the capsule have their leading setup subcommands (`cd`, `pushd`, `export`, `set`, `source`, …) stripped, as a slice of the original line | The capsule caps quoted commands at 160 characters and cuts from the right. One benchmark capsule reported its active failure as a `cd` into a 90-character absolute Windows path followed by `&& git restore...`, naming neither the test that failed nor the runner that ran it. Only a *leading* run is dropped and the remainder is returned verbatim, so pipelines keep their meaning; `commands.command_text` still stores the raw line, and `inspect --section failure` still shows it. |
| D61 | Above the hard ceiling the ladder may narrow `[DEAD_ENDS]` to its most recent entries and drop `[ACTIVE_SUBTASK]`, and a final backstop drops whole lines from the body | §16.3 protects the `DEAD_ENDS` *header*, not four entries of it, and does not protect `ACTIVE_SUBTASK` at all. With an honest estimator the spec ladder alone cannot always reach 1,000 tokens: a path or command made almost entirely of separators costs close to one token per character, so four dead-end lines at 200 characters each are 800 tokens on their own — the E2 property test found a 1,001-token case as soon as the estimator stopped under-reading. The backstop keeps the opening tag through `[STATUS]` and the `[RECOVERY]` tail, so whatever survives still closes its own tag, and it makes "≤ 1,000 tokens and ≤ 9,500 characters, always" a property rather than an expectation. |
| D62 | Schema v2 adds `file_stats.first_touch_ms` | D59 needs it, and it cannot be derived from the rows already stored. The migration seeds existing rows from `last_touch_ms`, so an upgraded database ranks no worse than before while new sessions get the real value. |
| D63 | Re-application requires a hash that identifies real content | `absent` and `unreadable` are sentinels, not digests: two of either compare equal without meaning the same bytes are on disk, so matching one against a dead end's post-edit hash proves nothing about the change coming back. |

## Defects found by the v0.1.2 Token-Burn qualification (evidence: tag `tokenburn-qualification-v0.1.2`)

| ID | Decision | Rationale |
|---|---|---|
| D64 | Exact continuation identifiers are first-class snapshot state: per-test status (`snapshot::test_statuses`, `crate::testids`), the most recent earlier message that names code when the latest names none (`snapshot::earlier_message`), and a ladder that sheds regenerable prose before identifiers | All four qualification restores lost a declared marker while the ledger held it. Replaying the frozen ledgers through the frozen code (byte-identical to the staged capsules) put the first loss at the snapshot for two markers -- a `LATEST` directive superseded by a sign-off; a fixed target test dropped because failures were modelled per command signature -- and at the renderer for the third, whose only carrier was failure-excerpt lines the ladder cut from 8 to 0. Test status is derived from rows already stored, so there is no schema change. A passing run clears a test only when it demonstrably covered it (same runner; whole suite, the test, its file, or its directory; selection flags only when their value matches), otherwise the test keeps its last observed state with its time. Messages count as naming code by a lexical rule (paths with an extension or two separators, `snake_case`, `camelCase`, `a::b`, `f()`, back-quoted spans), the same for every session. |
| D65 | `[REVERTED_EDITS]` prints one header per file; several reverts of one file share it (`3 reverts, 5 edit(s)`, then the last mechanism) | One qualification capsule spent three headers -- about 130 estimated tokens -- repeating one path, while the latest message naming the next function was cut for budget. Every attempt's excerpt and observation is still printed under the shared header, and `inspect --section dead-ends` still lists each dead end. |
| D66 | Files outside the workspace rank below every workspace file in `[FILE_ACTIVITY]` and `[RECENT_EDITS]` | In six of eight qualification source sessions the agent wrote Claude Code auto-memory notes under `~/.claude/projects/.../memory/`; they took two of eight working-file slots and both surviving recent-edit slots. They are demoted, not hidden: they are still listed once workspace files are exhausted. |
| D67 | `velra inspect --trace <MARKER>` reports PRESENT/ABSENT per layer (source transcript, stored events, ledger projections, snapshot, renderer, restored text, staged capsule), the first loss, and a reason read off the rows or the ladder rung | The qualification's own evaluator scanned only the staged capsule and labelled the result "what the ledger held", so three selection/render losses were reported as capture failures. Ladder rungs are now named (`render::render_ladder`) so a budget loss can say which rung removed a line. The reasons are computed, never inferred: when none applies the report says "other". |

## Found after the requalification freeze by a real VS Code session (source session `9d2f109f`, ledger replayed offline)

| ID | Decision | Rationale |
|---|---|---|
| D70 | Context a client injects around a prompt is not the user's words (`crate::prompt`): a complete element at the prompt's edge whose tag belongs to a known family -- `ide_*` (VS Code), `system-reminder`, `task-notification`, `command-*`, `local-command-*`, `bash-*`, `user-prompt-submit-hook`, and Velra's own `VELRA_*` -- is removed before intent classification and constraint extraction; a prompt made of nothing else changes no intent. The snapshot reads stored intents through the same rule, so ledgers reduced earlier restore correctly without a migration | The VS Code extension sends `<ide_opened_file>` as its own content block and `UserPromptSubmit` delivers it glued to the prompt, so the source session's ROOT *began* with "The user opened the file ... readme.md in the IDE" and the ladder kept that and cut the task. On the same machine three `<task-notification>` prompts had become a ROOT and thirty-three had superseded the user's latest message. The families are an explicit table, not "any leading tag", because the same client wraps a paste in `<pasted_content>`, which is the user's own task text; unknown tags, tags mid-prompt and unclosed elements stay authored. `events` keeps the raw prompt, so the trace still finds injected text at the source. |

## Found in the v0.1.2 pre-release hardening audit (staging and workspace identity)

| ID | Decision | Rationale |
|---|---|---|
| D105 | A staged capsule is one immutable record per stage, `staged/<workspace_id>/capsule.<gen>.json`, published by renaming a fsynced temp file to a name never used before. `<gen>` is `<sequence>-<nonce>`: the stage's clock in nanoseconds, or one more than the newest record present, and 80 random bits. A stage removes every older record by its exact name, record before claim; only the newest record is ever read for delivery. Every removal anywhere names one record or one claim | The single `staged_capsule` was renamed over by a restage and deleted by path after a delivery: reproduced, a restage made while a session start was delivering the previous capsule was deleted by that delivery's cleanup and never reached anyone. A name that is never reused cannot be a replacement. |
| D106 | The claim is the exclusive creation of `capsule.<gen>.claimed` beside the record, holding the claim time. Nothing ever removes or takes over another process's claim; a claimant checks that its record still exists after creating the claim, and a claim is removed only after its record or by a holder that did not deliver (`NotEmitted`, or a record that vanished). `CLAIM_LEASE_MS` only decides whether a held claim is reported `Busy` or `Interrupted` | The old marker was broken once its mtime was a minute old. Reproduced deterministically: a holder still working when its marker aged and the claimant that broke it both delivered the capsule, and two claimants that both saw an aged marker both won. A lease that can be broken always has a moment with two owners; a claim that cannot be broken has none. |
| D107 | Staged delivery is at most once. A session start that dies after writing the capsule to stdout and before removing it (the watchdog) leaves record and claim; no later session start delivers it, `velra status` reports it as claimed by a session start that did not finish, and `velra restore` stages it again. A newest record that cannot be delivered (unparseable, wrong version, hash mismatch, another workspace's id, too old, interrupted) is never replaced by an older record: removing an unparseable or stale newest record removes the older ones with it | Reproduced through the real hook: killed by its watchdog after its emit, the capsule was delivered again to the next session once the marker aged. The filesystem cannot say whether the first output reached Claude Code, so the choice is between a possible duplicate injection and a restore repeated by hand; the second is visible and loses nothing the ledger does not still hold. Supersedes the "claim left by a crashed process expires after 60 seconds" recovery (docs/RESTORE.md). |
| D108 | `velra restore`, `status` and `inspect` resolve the workspace through `workspace::resolve_recorded`: with `CLAUDE_PROJECT_DIR` set, the hook's answer; otherwise, inside a repository, the nearest directory from the current one up to the repository root that the ledger has a session recorded under, else the hook's mapping. Outside a repository only the current directory is tried. `inspect`'s own copy of the mapping (`project_id_for_cwd`, which ignored the variable) is removed. The environment variable is a parameter of the internal functions, so unit tests do not inherit it | Claude Code sets `CLAUDE_PROJECT_DIR` to the directory it was started in; a terminal has no such variable and the mapping gave it the repository root. Reproduced with the hook and the CLI in separate environments: a session started in a monorepo package was recorded under the package's id while `velra restore` in that package listed and staged under the root's, so the capsule was never delivered. The existing agreement tests passed because the harness gave the CLI the variable too. |
| D109 | The CLI names the workspace root it resolved: `velra restore` says to start the new session in it, `--json` carries `workspace_root`, an empty listing names it with the hint to run from where Claude Code was started, and `status` names it on the `Staged:` line | A resolution the CLI cannot make agree -- a subdirectory of a directory that is not a repository -- is then visible where it happens rather than silent at the next session start. |


## Found in the v0.1.2 pre-release hardening audit (in-session continuation)

| ID | Decision | Rationale |
|---|---|---|
| D110 | A delivery key already recorded in `injections` writes nothing: `continuation::deliver` returns `None` without calling `emit`. Supersedes §15.5, which re-emitted the recorded capsule. `Delivery::replay` is removed | The same key twice is the same hook invocation run twice -- Velra registered for one event under two binary paths (user and project settings, which Claude Code does not deduplicate), or two session starts in one millisecond. Reproduced through the hook: a prompt delivered to two copies of the hook wrote the capsule twice, and the replay wrote a checkpoint's capsule after a later compaction had superseded it. Claude Code does not retry a hook, so the replay served no case that occurs. |
| D111 | A spooled `checkpoint_request` (PreCompact that could not reach the database) makes its checkpoint wherever it is folded -- incrementally, or inside a rebuild at its logical position -- at most once (a checkpoint whose `event_watermark` is the request's id is its own), and only while it is the session's newest compaction: not when the session has a checkpoint created at or after the request's time, nor when a later PreCompact or request, a `SessionStart(clear)`, or a `SessionEnd(clear\|logout)` follows it in logical order (`reducer::checkpoint_request_is_current`) | Two reproductions. A rebuild skipped every request as "already acted on", including one it was folding for the first time -- every request that arrives behind a later event, such as the `SessionStart(compact)` a moment after the PreCompact that spooled it -- so the checkpoint was never made and the continuation silently lost. And a request folded incrementally after a newer direct checkpoint superseded it, putting an older compaction's continuation in its place. Folded inside the rebuild, the checkpoint is built from the state at the compaction boundary rather than at whatever moment the spool happened to be drained. |
| D112 | No continuation older than `PENDING_TTL_MS` (7 days from its checkpoint) is written out on any channel: `deliver` expires a live continuation past it, PENDING or ATTACHED, instead of emitting | Expiry was `reconcile`'s alone, and the PostToolUse channel delivers a PENDING continuation without reconciling first. Reproduced: a checkpoint 7 days and 1 ms old was delivered on every channel, and an ATTACHED one was re-emitted on the prompt channel. A pause of any length (a laptop asleep) is only a gap between two hook timestamps; the TTL decides, and tests state it on the hooks' clock, not by sleeping. |
| D113 | `CONFIRMED` means: after the last attach, the same session recorded a tool call (`PostToolUse`, `PostToolUseFailure`) or a turn end (`Stop`) -- the session went on past the delivery. `ATTACHED` means the capsule was written to stdout and that write committed. Neither means Claude Code kept the context or that a model read it. The stored names are kept (the schema's `CHECK` names them, and nothing user-facing claims receipt); `continuation::meaning` is the one wording, and `velra status` prints the latest continuation in any state with it (`--json`: `latest_continuation`) | The hook protocol returns nothing to a hook: exit 0 and a JSON object on stdout are all Velra controls. The strongest signal the protocol offers is that the session produced another event after the delivery, and that is what confirmation reads. A stronger one exists outside the protocol: Claude Code 2.1.x writes a `hook_additional_context` attachment into the session transcript (observed in this machine's own transcripts). Velra does not read it -- the transcript format is Claude Code's internal format -- so it is left to the human end-to-end check. The E2E checklist expected `velra status` to show `CONFIRMED`, which it could not: it listed live continuations only. |
| D114 | The watchdog cannot end a hook between writing a continuation's capsule and committing its delivery: `hook::DELIVERING` is held from just before `emit` until `deliver` has committed or rolled back, and the watchdog takes it before exiting. The latency this adds is one commit | Reproduced with a stall after the write (`VELRA_TEST_STALL_AFTER_CONTINUATION_EMIT_MS`) and a short watchdog: the process exited with the transaction open, the continuation stayed PENDING, and the next tool call delivered the capsule again as if it were fresh. Emit-then-commit is kept, because commit-then-emit would record a delivery that a process dying before the write never made, and later activity would then CONFIRM it. A process killed from outside in the window (not the watchdog) can still deliver once more, the same kind of repetition the prompt channel's T4 re-emission makes on purpose. |
| D115 | The continuation path is described as *once per delivery point*, not *exactly once*: each hook invocation writes the capsule at most once; after the first write no other channel writes it; the prompt channel alone writes it again, up to `MAX_ATTACH` times in all, when the previous turn left no evidence (T4). The README, CONFIGURATION and ARCHITECTURE wording is corrected. The continuation capsule's preamble ("this session's own prompts") is true on this path because delivery is keyed by the exact session id; the restored (cross-session) capsule's identity and preamble are a renderer change outside this path | "Exactly once" was never true of this path by design (T4), and D114's residual window is a second way it is not. What holds, and is tested, is that a continuation reaches only its own session, is never written twice by one invocation or by two channels, and is never CONFIRMED without a committed write. |
